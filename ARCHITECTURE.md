# Architecture based on the installed game

## Verified engine boundaries

KillingFloor.exe and its Engine/Core/D3D9Drv modules are x86. The active render device is D3D9Drv.D3D9RenderDevice, confirmed by live UObject inspection and native callbacks. D3D8 is also imported by the launcher; that import does not identify the active renderer.

Packages use UE2 version 128/licensee 29. The package reader recovered 2,381 TextBuffers and class inheritance records with no source decoding errors. These TextBuffers contain script declarations and bodies, **not a complete defaultproperties export**. The weapon audit separately reads verified live UClass default buffers; 83 of 96 weapon-derived classes were loaded with usable defaults. The initial install lacked UCC; the official Steam SDK is now installed and provides the compatible compiler/script sources. Native C++ SDK headers remain absent.

Script-visible mechanisms include PlayerCalcView, WeaponFire.GetFireStart and AdjustAim, KFWeapon.ReloadMeNow/ConsumeAmmo/AddReloadedAmmo, Actor.Trace, GetBoneCoords, SetBoneDirection, SetBoneLocation and SetBoneRotation. Canvas.DrawPortal exists, but a symmetric FOV portal alone does not provide OpenXR asymmetric projections, resource ownership or frame submission.

Native exports include UGameEngine::Tick/Draw, FPlayerSceneNode::Render, FCameraSceneNode::UpdateMatrices, and D3D9RenderDevice::Lock/Unlock/Present/ReadPixels. Export names supply concrete x86 signatures. Core accessor instructions and object index/class/name relationships validate the read-only reflection profile. Native addresses are resolved per process; no Refractor or Frostbite offsets were imported.

## Selected direction

`KF x86 native adapter -> private eye surfaces -> D3D11 pair transport -> x64 OpenXR host`, with KFVR UnrealScript gameplay/replication layered on the existing KF classes. The x64 host avoids depending on a 32-bit headset runtime. The installed runtime registry points to SteamVR's x64 manifest; no WOW6432Node runtime registration was observed.

An engine scene/camera integration plus a graphics transport is the current candidate. A full custom UE2 render device would require an unaudited legacy native ABI and much more renderer work. Intercepting D3D9 Present alone supplies one already-rendered image and cannot implement correct stereo, culling or physical aiming.

**Not yet solved:** the verified FPlayerSceneNode callback must still be audited for render-side animation, visibility/LOD, occlusion, particles, temporal effects, first-person weapon and post-processing ownership before it can be replayed. The successful trace proves no *engine Tick* occurs within Draw; it does not prove all rendering is free of simulation-like side effects. Bounded developer trials now replay FCameraSceneNode world views; persistent replay is not enabled. An expanded nine-hook trace found script HUD/UI callbacks and skeletal GetFrame calls during Draw; the two instrumented animation-advance functions had zero calls inside Draw in the sampled lobby and match. KFWeapon.RenderOverlays changes weapon location/rotation in the installed script. FLevelSceneNode::Render ran twice per ordinary Draw. The probe uses nesting depth to trigger only at the outer world view. GetFrame also writes pose caches; zero animation-update calls does not mean it is side-effect free.

The native device is non-Ex D3D9 with 8x MSAA in the captured session. A future D3D9Ex promotion path needs its own resource-pool/reset compatibility work. A non-Ex D3D9 CPU bridge now resolves and transports two supplied eye surfaces into the D3D11 pair stream. An isolated 32-bit D3D9 producer/64-bit consumer verified all pixels, RGBA/BGRA order, alpha, MSAA, backpressure, discarded-stream recreation and device reset. It never renders the eyes itself or changes native render-target bindings. Callers must release it before native device reset. The 256 MiB aggregate working-resource cap excludes caller-owned source surfaces and driver overhead. Measured transfer cost was 4-6 ms at 1024x768 and 16-25 ms at 2048x2048 with 8x MSAA in the second probe run; this is a prototype fallback, not a validated VR performance path. GPU sharing must use same-adapter, compatible non-MSAA shared resources. See [Microsoft's sharing requirements](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11device-opensharedresource).

## Frame and camera invariants

- One native simulation/animation advance supplies both eyes. Pair identity includes frame, resource epoch, reference space and predicted display time.
- Both images must exist and be restored to a clean native state before publication. An incomplete pair is dropped.
- UE world axes are X forward, Y right, Z up. Camera matrices use row vectors, with right/up/forward rows. Native near plane observed as 5 UU; perspective depth approximately 65536 UU. Values are observation, not globally fixed constants.
- KF's inverse-rotation constructor negates rotator units before its 14-bit lookup. The camera adapter matches this quantization and the captured native basis.
- Scale is explicit, never borrowed from Battlefield. Physical calibration remains pending.
- Keep head, body heading, locomotion, weapon aim and recoil separate. Do not teleport the server pawn to follow room-scale movement.
- Persistent stereo capability remains disabled. A bounded native-to-OpenXR bridge now repeatedly renders fresh private targets/cameras with exact RHI restoration and real HMD poses/FOVs. Temporal resources, image stability and map/device lifecycle acceptance remain pending.

## Gameplay and ammunition

KF AmmoAmount already includes loaded rounds. Stock ConsumeAmmo decrements the native ammo total and magazine count; AddReloadedAmmo selects a loaded count from that total rather than adding rounds. KFVR must take authority over reload transitions when enabled so classic reload notifications cannot also credit ammo.

AmmoMachine owns chamber, inserted magazine/tube, retained hand magazine, reserve, spent and discarded rounds. Every accepted transition conserves the initial budget. Clients request actions without supplying round counts. Sequence/ownership epoch and trusted server time reject stale/replayed commands. Switching, death and drop cancel pending gestures without reversing completed physical operations. Fire cadence survives suspend/re-equip.

This accounting currently supports closed-bolt detachable magazines and tube-fed manual/self-loading weapons. Revolvers, break actions, dual independent guns, magazines as inventory objects, pickups/trader integration and special weapons require additional authoritative adapters. Profile timings must be derived from the native weapon/perk state; example defaults are not a final balance decision. Snapshot correction is a trusted-server API, not a client RPC.

MeleeGate returns bounded attack eligibility and a segment, not damage or a trusted hit. Integration still needs authoritative swept traces, weapon-specific arcs/range/damage/cooldowns and velocity evidence that accounts for packet loss. The 58-byte pose codec is an engine-independent transport design, not yet a KF replication implementation.

## Controllers, IK and UI

OpenXR Actions supports Khronos Simple, Oculus Touch, Valve Index, Microsoft motion controllers and Vive bindings, with separate grip and aim poses. Only focused, valid tracking produces controls. Haptics are capped at 250 ms and suppressed without focus. The x64 host publishes controller samples over a separate mailbox inside the version-2 frame channel. Input delivery and neutral releases do not require an eye pair. Samples expire after 100 ms; focus/recenter transitions cancel old haptics. Reverse feedback uses one-shot sequence IDs. Both directions passed a real x64/x86 process test. A bounded left-stick adapter now binds this mailbox to the measured positive-input PlayerTick boundary; its first live movement/release check passes; physical left-stick control is accepted, while weapon bindings remain pending. Standard bindings follow the [OpenXR specification](https://registry.khronos.org/OpenXR/specs/1.0-khr/html/xrspec.html).

Bone APIs make a script-first remote-pose prototype plausible, but KF skeleton topology, bone spaces, animation timing, dedicated-server behavior and render-thread ownership still need verification. The imported restoration cache avoids reusing previous IK results as authored animation and keys state by actor/skeleton generation. It is not a complete KF full-body solver.

Menus/HUD need their own VR plane or quad layer, controller pointer and focus handling. Existing pickups/trader rules remain the baseline. Scopes and procedural legs/feet follow working stereo, input and authoritative weapons.

## Crossplay decision

Flat and VR players should share a KF server and normal KF game rules. An unchanged flat executable can load UnrealScript packages supplied by the server; Engine.Mutator.bAddToServerPackages and AddToPackageMap exist in the installed source. A completely vanilla package set has no consumer for new head/hand targets and cannot invent custom IK.

The target is therefore **B: a KFVR gameplay/client package shared by VR and flat clients**, with no HMD requirement for flat users. Automatic package download still needs an actual server/client test. If script bone controls prove insufficient, full remote body rendering may additionally require a small native flat-client addon. This is an unresolved acceptance item, not a promise of zero installation. Existing unmodified public servers cannot validate new manual reload/melee rules. Perk/stat eligibility and whitelist behavior must be tested separately; local progression compatibility is not proof of official online stat compatibility.

D3D9 transport follows the documented [GetRenderTargetData constraints](https://learn.microsoft.com/en-us/windows/win32/api/d3d9/nf-d3d9-idirect3ddevice9-getrendertargetdata), [MSAA resolve path](https://learn.microsoft.com/en-us/windows/win32/api/d3d9/nf-d3d9-idirect3ddevice9-stretchrect) and [adapter LUID mapping](https://learn.microsoft.com/en-us/windows/win32/api/d3d9/nf-d3d9-idirect3d9ex-getadapterluid). A temporary D3D9Ex enumerator identifies the adapter; it does not replace/promote the original device. Copying bytes with explicit channel order does not calibrate KF gamma/exposure.

The ammunition policy also compiles as KFVRGameplay.KFVRAmmoState inside the actual KF scripting engine. A commandlet passed 30,059 checks; 20 rolling state/result checkpoints agree with the C++ reference over 20,000 actions for detachable/self-loading and tube/manual profiles with ownership changes. This is regression evidence, not proof of complete behavioral equivalence. The script boundary uses nonnegative 31-bit sequence numbers and bounded monotonic integer milliseconds; a native/client adapter must convert this explicitly. Neither policy accepts client-supplied counts. KF inventory/fire/reload notifications are not bound to the policy yet.

The native target-management experiment now passes on the audited build: a native FAuxRenderTarget is bound, cleared, popped and destroyed; original GPU bindings and all 0x594 cached RHI bytes match afterwards. Pixel readback occurs from an AddRef-retained private surface at Present, outside scene submission. This is a bounded developer probe, not a persistent eye renderer. Fresh camera construction and derived visibility data now pass native comparisons; broad culling/LOD coverage and repeated render-side effects remain separate work.

A bounded native stereo diagnostic now produces two actual world images using fresh FCameraSceneNode instances with parallel camera offsets and separate FAuxRenderTargets. It calls FCameraSceneNode::Render, not the full FPlayerSceneNode/HUD/weapon-overlay loop. The original player scene is never edited. The observed world-render path still invokes HUD.WorldSpaceOverlays and skeletal GetFrame; their repeated-frame behavior remains unresolved. Images are read at Present. The later bounded eye bridge connects these world views to XR game-image submission; a persistent player runtime remains unfinished.

The complete camera adapter emits six related matrices, origin, per-pixel world differentials and determinant together (106 floats, matching the audited private-node range 0x14..0x1bc). It uses an exact inverse for the near-rigid camera basis and the explicit asymmetric perspective inverse. Native constructor comparisons over five poses/FOVs differed by at most 0.0001221. Synthetic head translation/rotation and separate asymmetric eye frusta now drive fresh native nodes and produce actual world images. Synthetic 50 UU/m, 64 mm eye separation and test frusta are diagnostic parameters, not headset calibration. The observed four extra HUD callbacks dispatch the inherited WorldSpaceOverlays implementation, which conditionally calls DrawRoute when debug display is enabled; no global callback suppression is used.

Physical hardware checkpoint: the x64 OpenXR presenter now renders the synthetic diagnostic room on the connected headset. The user confirmed stable head response and both haptics; per-hand telemetry verifies tracking, triggers, grips and sticks. No runtime or binding changes were required. This validates the presenter/actions hardware boundary independently of the subsequently connected native KF eye-image producer. See docs/HEADSET_TESTING.md for evidence and limits.

The native eye bridge accepts channel requests at the verified world render boundary and transfers complete pairs at Present. D3D9 Reset is protected before retaining default-pool resources; device loss, world ownership changes, host loss and time limits stop the bridge. Cleanup belongs to the graphics thread. If that thread cannot acknowledge cleanup, the report is incomplete and hook removal is withheld rather than releasing GPU resources on the worker. Each pair still verifies original camera bytes, target canaries and RHI restoration.

OpenXR distinguishes fresh-pair acceptance from bounded reprojection. A fresh pair must match the exact requested tracking sample. Between updates, the host may reference the last complete released swapchain pair for up to 100 ms using its ORIGINAL render poses/FOVs. It never substitutes new view poses on old images. Focus/tracking loss, a reference-space change, size/adapter mismatch or an attempted incomplete swapchain update prevents retention. Fresh and reprojected submissions are counted separately. This follows xrEndFrame's most-recently-released-image semantics: https://registry.khronos.org/OpenXR/specs/1.0/man/html/xrEndFrame.html

The locomotion trial reads focused, unexpired left-controller samples on the verified game/graphics thread. It requires a live, owned pawn in the original standalone world and no LevelInfo.Pauser. Raw-stick radial neutral is required after focus/tracking loss, ownership/reference changes, stale input or a clock discontinuity. During one normal PlayerTick it temporarily supplies aBaseY/aStrafe, lets existing KFPlayerInput/PlayerMove process them, then restores both previous raw properties. The callback pair stays counted during shutdown until restoration completes. Request ABI v9 carries reflected ownership/health offsets. This remains opt-in and bounded; nonzero scaling, corresponding pawn displacement and native cleanup pass the first live standalone trial. Physical headset movement was subsequently accepted on September 25.

Right-stick snap turns are injected at the existing KFPlayerController.UpdateRotation call inside the normal PlayerTick, after stock FOV/weapon sensitivity. The one-shot aTurn addition is degrees * 65536 / 360 / (32 * DeltaTime); the prior input axis is restored after that native script call. Left/right tracking policies are independent. A live native trial measured all three requested 30-degree turns and exact input restoration. This is body heading, not controller weapon aim.

The default headset launch requests 100% of the runtime-recommended eye dimensions and runs for 120 seconds, with an explicit 180-second cap. The actual recommended 2064 x 2208 dimensions passed the native receiver trial. The CPU pair bridge remains a performance bottleneck; full resolution does not establish headset-rate fresh-frame delivery.

The new PhysicalReload ledger handles one or two closed-bolt detachable-magazine guns with persistent magazine identities and a shared supply. Geometry gates drive physical seating and partial/full action strokes; BeltReloadSession combines two independent docks with that one ledger. TrackedWeapon provides head-independent controller/model/muzzle transforms. The compiled KFVRReloadVisual samples four authored animation ranges on a presentation-only actor. These modules are not yet wired into live KF weapons. The physical ledger and old AmmoMachine/KFVRAmmoState must not both credit the same ammunition. See docs/MANUAL_RELOAD_INTERACTIONS.md for the exact current boundary and remaining calibration/server work.

The September 27 standalone weapon increment is documented in docs/TRACKED_WEAPONS.md. Native request ABI v12 reflects a 124-byte game-thread tracking packet and a 28-byte script-to-native feedback packet. The live pistol adapters use standard WeaponFire ticking and ammo consumption, with a separate script magazine ledger in physical mode. Model/palm placement is independently measured from KF assets and separate hand actors render in both world views.

## Live inventory and physical reload adapter

The standalone rig now registers Single, Deagle and Bullpup adapters with independent world models and right hip/left hip/right shoulder slots. Drawing calls the normal pawn weapon-change path. All three retain native stock firing/perks/ammunition; right B invokes the stock timed reload except while the 9mm's physical mode is enabled. Registration prunes stale ownership and rebuilds visual hands on a pawn change.

`KFVRMagazineState` is the live single-pistol authority, separate from the portable dual-gun prototype. It retains magazine identities/partial contents, a chamber and loose reserve. Script gestures call it only on the ordinary rig Tick. The weapon's successful stock ConsumeAmmo callback mirrors exactly one spent round; presentation cannot credit ammo. Timed reload entry points are blocked in physical mode. External ammo changes adjust its owned budget. Switching retains an offhand magazine and cancels incomplete action travel. Physical duals, server replication and complete trader/drop rules remain open.

The model's palm, support, magazine and slide locations are measured from installed assets. UE2's bone translation import scale is measured across ordinary frames because BoneRefresh does not invalidate the same-frame animation cache. Magazine position/orientation follows the left hand. A shortest-rotation solver aligns the Bullpup's authored grip-to-support vector with both controllers while retaining dominant-hand roll.

Frame-channel input reads now allow a bounded 1 ms mutex wait to avoid turning brief frame-request lock overlap into a false tracking-loss edge. The original 100 ms ControlWire deadline, neutral invalid/focus-loss behavior, peer identity and close checks remain in force. No cached packet has its lifetime extended.

The knife has a separate body-relative motion gate and contact sweep. It measures blade motion relative to pawn position/body yaw, arms only after settling away from its left-shoulder dock, rejects tracking jumps, preserves cooldown across tracking loss, and requires retraction. It replaces the desktop camera cone with a short blade sweep window, sending the installed damage amount/type into TakeDamage. World captures verify the visible blade; exact contact calibration and zed/perk acceptance remain open.

Script feedback now retains independent hand serials. Native ABI v12 validates the 28-byte feedback packet; shared-channel v3 acknowledges consumed pulses by clearing the mailbox, and preserves unread opposite-hand pulses without extending their expiry. This removes both script-side and transport-side hand overwrites. Native bootstrap rejects old request versions.

The standalone dual-9mm path now selects KFVRDualMagazineState while belt reload mode is enabled. Both fire modes share one stock ammo object and one identity/reserve ledger; successful stock consumption is mirrored exactly once. KFVRBeltInsertion is a per-hand geometry gate driven on the ordinary game-thread rig Tick. It blocks stock timed reload notifications, retains partial magazines across switching and restores the timed feed adapter on explicit mode exit. KFVRStatusDisplay is a presentation-only native-world mesh and private ScriptedTexture. Its ordinary rig Tick captures health/armor and selected-weapon state, positions the card from the offhand/head, and advances its texture revision only on data changes. The standalone tracked syringe derives from the installed Syringe and both installed fire modes. The optional arm prototype solves two measured skeleton segments around a body-relative shoulder/pole and preserves controller palms. Native bone readback validates the actual applied result. KFVRGrenadeControl retains the exact installed Frag inventory object so the pawn's cached grenade and desktop quick-throw path remain valid. Frame-channel mapping v4 retains a completed request ID/outcome while permitting the host to queue its next request. Full-resolution receiver throughput improved in a controlled live comparison; headset cadence remains unaccepted.


## Runtime controller presentation frame

The September 30 physical pose capture measured a stable approximately 60-degree orientation difference between grip and aim on the active controller profile, plus approximately 10 cm between their origins. NativeWeaponRig now constructs presentation from validated grip position and runtime aim orientation before applying the common reference/body transform. Both validity bits are required; no fixed controller angle or aim-origin translation is applied. Raw controller data, wire layouts and head/eye transforms retain their previous definitions. The hand diagnostic deliberately separates grip and aim in a translated/yawed tracking space.

Installed syringe/welder meshes have upward-pointing idle working axes. KFVRWeaponVisual measures an orthonormal working frame and applies its inverse before the controller presentation frame, keeping the measured palm anchored. The rig transforms contact endpoints and trace direction through that actual model rotation. Rendered bone direction is observed independently for regression checks. The bounded external observer builds fresh object inventories on a separate read-only handle while continuing pose samples, avoiding discovery-sized gaps in short interaction phases.


## Optional native hand assets

`prepare_native_hands.py` converts the installed 9mm hand mesh into a separate local-only package. It preserves bind geometry under a rigid palm-frame transform, retains sixteen bones per hand, maps helper influences into the palm, and closes a geometric wrist cut. ActorX child rotations use the conjugated convention. Shared skin points and descending influences are required by the currently verified path; triangle-expanded input rendered torn palms despite preserving exported geometry and passing bone checks.

The normal gameplay package dynamically loads these meshes only when the private URL requests NativeHands. It takes the installed character hand material from the owned pistol after stock sleeve swapping and retains each native finger's measured roll while driving its pointing axis. No extracted geometry is compiled into KFVRGameplay. Staging validates all selected package/source hashes and existing destination ownership before copying. The developer arm experiment is a mutually exclusive mode.

Both hand options now initialize as hidden actors during the living standalone pawn's ordinary Tick, before tracking starts. Visibility, poses and release still follow validated tracking on that Tick. The same preload path is covered by the default-hand regression; this does not establish a headset performance improvement. See docs/NATIVE_HANDS.md for local preparation and limitations.
